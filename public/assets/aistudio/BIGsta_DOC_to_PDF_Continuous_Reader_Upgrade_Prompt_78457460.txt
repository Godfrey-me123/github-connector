AREA 2 — DOC/DOCX CONVERSION IMPLEMENTATION
A. Inspect package.json and existing dependencies first. Reuse an existing client-side converter if available. Otherwise choose and add a maintained browser-compatible implementation with minimal dependencies, then update the lockfile if the project uses one.
B. Prefer a real browser-side DOCX-to-PDF pipeline. Options to evaluate include docx-preview for page-like Word rendering followed by a reliable PDF export path, or Mammoth for DOCX-to-HTML plus a PDF generation library. Choose based on actual project compatibility and output quality; do not combine libraries unnecessarily.
C. Important: Mammoth converts DOCX to semantic HTML and does not itself generate PDF. If selected, implement the PDF-generation stage explicitly.
D. Legacy binary .doc is not the same format as .docx. Do not claim full .doc support unless the chosen library genuinely supports it. If only .docx is supported, label the picker “Word documents (.docx)” and explain that legacy .doc must first be saved as .docx or PDF. If an existing trusted conversion route supports .doc, integrate it without silently uploading files.
E. Preserve the original document. Conversion must create a separate PDF result and never overwrite/delete the source Word file.
F. Preserve headings, paragraphs, lists, tables, images, page breaks, margins, and reasonable spacing as well as the chosen browser-side library allows. Use appropriate page dimensions (default A4, with a settings option if practical), padding/margins, and page-break handling. State honestly that browser conversion may not match Microsoft Word pixel-for-pixel, especially for unsupported fonts, complex layouts, headers/footers, floating shapes, and page numbering.
G. Do not inject untrusted DOCX content unsafely into the app. Sanitize any generated HTML before rendering, isolate conversion preview where appropriate, and avoid executing scripts or event attributes from document content.
H. Show useful conversion progress/status only when measurable. Do not freeze the UI for large files; use asynchronous processing and provide a cancel/retry path where feasible.
I. Name output sensibly, e.g. original-name.pdf. Offer “Preview PDF”, “Download PDF”, and “Print / Save as PDF”. Keep original and output distinguishable.
J. Store the generated PDF in the existing PDF Library/IndexedDB if the current PDF Library architecture supports it. Store metadata and the PDF Blob together; ensure large files and quota errors are handled. Do not store a temporary blob URL as persistent data.

AREA 3 — FIX THE PDF ZOOM BUG PROPERLY
Current problem: zooming appears to make the document extend farther down instead of enlarging/shrinking the visible PDF page correctly. Diagnose the real cause in the current reader before patching.
A. Identify whether pages are rendered as canvas, images, iframe/native browser PDF, or HTML. Implement zoom appropriate to that rendering architecture rather than merely increasing container height or adding arbitrary margins.
B. Zoom in/out must scale the actual page content and page width. For a canvas-based PDF.js renderer, render each page using the selected scale/viewport and update canvas pixel dimensions and CSS dimensions consistently (including device-pixel ratio if used). For an HTML/page renderer, apply a correct page scale transform or layout scale and ensure the scroll container dimensions match the scaled content. Avoid scaling only the outer wrapper while leaving the rendered canvas at its old resolution.
C. Do not make zoom appear to work by adding blank height, padding, or page margins. The page itself must visibly enlarge/reduce.
D. Add a visible zoom toolbar with:
- Zoom out button
- Current zoom percentage (e.g. 100%)
- Zoom in button
- Reset to 100%
- Fit width
- Fit page
- Optional selectable percentage presets (50%, 75%, 100%, 125%, 150%, 200%, 300%)
E. Use a sensible minimum/maximum zoom (for example 50% to 300% or 400%), prevent values outside limits, and ensure repeated clicks do not accumulate CSS/layout errors.
F. Fit width should fit the PDF page to the available reading viewport width while preserving aspect ratio. Fit page should fit both width and height of one page inside the viewport. Reset should restore actual-size/100% behavior.
G. On zoom changes, preserve the user's approximate reading position/page when possible. Avoid unexpectedly jumping back to page one or the top after every zoom.
H. If a canvas renderer is used, rerender pages at the requested scale and avoid stale asynchronous renders overwriting newer zoom settings. Cancel or disregard stale render tasks. For long documents, render lazily or in visible batches to prevent excessive memory use.
I. Make zoom controls usable on desktop and mobile. Support Ctrl/Cmd + plus, Ctrl/Cmd + minus, and Ctrl/Cmd + 0 only when the PDF viewer is active and do not hijack normal typing in inputs.
J. If native browser PDF iframe rendering is the reason custom zoom cannot reliably control the actual PDF, replace only the reader rendering layer with a proper client-side PDF viewer (prefer the existing PDF.js dependency if available, otherwise add it carefully). Do not fake custom zoom controls that cannot affect the actual PDF.

AREA 4 — CONTINUOUS VERTICAL PDF READING (WPS-LIKE)
A. For multi-page documents, display all pages in one continuous vertically scrollable reading area, in page order. The user should scroll naturally from page 1 through the final page, like WPS Office.
B. Remove the requirement to click “Next” to advance through each page. Remove/hide previous/next page buttons from the primary reading flow. Do not implement one-page-at-a-time navigation as the default.
C. Keep page boundaries visually clear using a white page surface, subtle border/shadow, consistent page gaps, and a neutral reader background. Keep page dimensions and aspect ratios correct.
D. Keep the top toolbar usable while scrolling (sticky toolbar if compatible with the existing layout). The scroll area should be independent and should not make the whole app page jump unpredictably.
E. Provide page count and optional current visible page indicator (e.g. “Page 4 of 28”) as informational feedback, not as a required Next/Previous workflow. A page-number field or thumbnail jump may be included as optional shortcuts, but continuous scrolling remains the default.
F. If page thumbnails are feasible within the existing architecture, add a collapsible thumbnail sidebar/panel that jumps to a page. Do not block core scrolling functionality on this enhancement.
G. Keep rendering efficient for large PDFs: render visible pages first, use lazy rendering/IntersectionObserver or the PDF library's equivalent, clean up canvases/render tasks when documents close, and display page placeholders/loading indicators for not-yet-rendered pages.
H. Make sure vertical scrolling still works at high zoom. At high zoom, horizontal overflow may be allowed inside the viewer, but must not disable vertical scrolling or crop content without a way to pan horizontally.
I. Support mobile touch scrolling and avoid accidental text-selection/drag behavior that prevents reading.
